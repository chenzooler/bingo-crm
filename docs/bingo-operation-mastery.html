איך בינגו באמת עובדת — פירוק מלא של מכונת בדיקות הזכאות

מדריך המאסטר להבנת מערכת האוטומציה של בינגו: תוסף Chrome שממלא טפסי הלוואות אצל חמישה גופי מימון ישראליים, קורא לידים מ-Yoatsim CRM, ומוליך כל בקשה עד לרגע ה-OTP. המסמך הזה הופך את הקורא למומחה אמיתי לתפעול של בינגו — לפני שבונים מחדש את ה-CRM.

5 גופי מימון 17 נציגים agent.js ~9,000 שורות Engine V4 · server-brain Voicenter · OTP טלפוני Fable 5 / Opus AI-fallback
01

סקירת המערכת — הארכיטקטורה האמיתית

בינגו היא סוכנות תיווך אשראי מורשה. הנציגים מבצעים בדיקות זכאות בזמן אמת מול חמישה גופי מימון ישראליים, על ידי נהיגה אוטומטית בטופס האינטרנטי הציבורי של כל גוף. הלקוח על הקו, נותן OTP אמיתי — ולכן כל בדיקה כושלת שורפת אמון ו-OTP של לקוח אמיתי. זו הנקודה שממנה נובע כל מבנה המערכת.

בפועל יש כאן שלושה מוחות שרצים במקביל על אותו לקוח, ולעיתים על אותו מסך — וזה מקור עיקרי לכאב (ראו §7):

מקור הנתונים
Yoatsim CRM
ה-CRM התפעולי (app.yoatsim.co.il). הליד יושב ב-Angular scope. הרקע קורא client.json[code] ישירות מה-scope (world:MAIN).
מתזמר
background.js
MV3 service-worker. קורא CRM, מנתב ~50 הודעות, מנהל תור OTP טורי, proxy residential, פותח טאב לכל גוף, שער ל-Anthropic.
מוח מבצע
agent.js + Engine V4
content-script שממלא את טופס הגוף. הישן = היוריסטיקות + AI-fallback. החדש (V4 server-brain) = ScreenRunner דטרמיניסטי לפי playbook.
ממשק נציג
popup / sidepanel
הנציג בוחר גופים + סדר עדיפות, מריץ, רואה סטטוס חי לכל גוף, מזין OTP, רואה תוצאות והיסטוריה.
Yoatsim ⟵ קריאה · background ⟶ פותח טאב לכל גוף · agent/V4 ממלא ⟶ OTP לנציג ⟶ reportResult ⟶ mirror-server + webhook
מוח שרת
mirror-server (v3)
Node/Express חד-קבצי. בולע כל אירוע טלמטריה מכל נציג, דשבורד חי, טוען selectors חמים דרך /api/config.
גשר
engine-v4-bridge
מריץ את ScreenRunner בכל דף גוף, מציג overlay ממותג של OTP/כרטיס/handoff, מדווח done/stuck/manual.
ערוץ OTP
Voicenter / טלפוני
ה-OTP תמיד לנייד הלקוח. הנציג מבקש בטלפון את 6 הספרות, מדביק ב-overlay שמוזרק לטאב ה-CRM.
רשת
Proxy residential IL
רק דומייני הגופים מנותבים ל-IP ישראלי מסתובב (PAC). IP טרי לכל בדיקה, יציב בתוך בדיקה כדי שה-OTP/session ישרדו.
עיקרון-על המהלך האסטרטגי של חן

להעביר את כל לוגיקת הבוט מ-agent.js השברירי (~9,000 שורות, selectors קשיחים) אל מוח מרכזי בשרת. באג בסלקטור היום = 50 נציגים שבורים ויום של ZIPים. אחרי המעבר: תיקון JSON על השרת = 60 שניות לכל 17 הנציגים דרך /api/config. "מהיום והלאה — 0 ZIPים."

שני מנועים חיים זה לצד זה. engineMode קובע מי שולט: ברירת המחדל היא V4 (המנוע החכם מטפל בכאל/ישראכרט/פניקס, והבוט הישן עוצר אוטומטית עם ההודעה "מנוע חכם מטפל"); engineMode='legacy' הוא כיבוי-חירום ידני שמחזיר הכל לבוט הישן. בנק ירושלים ומקס עדיין נשענים במידה רבה על הבוט הישן.

02

זרימת העבודה המלאה של הנציג — מהליד ועד התשלום

כך נראה מסלול חיים של בדיקה בודדת, מהרגע שהנציג פותח לקוח ב-Yoatsim ועד לתוצאה. השלבים באדום הם רגעים קריטיים / התערבות אנושית מכוונת.

שאיבת הליד מ-CRM
הנציג פותח לקוח ב-Yoatsim ולוחץ "קרא מ-CRM" / "שאיבה מ-CRM". ה-background מוצא את טאב app.yoatsim.co.il, מריץ סקריפט ב-world:MAIN, שולף את angular.element('.ng-scope').scope().client וממפה את קודי client.json לאובייקט ליד מנורמל. הסטטוס: "✅ נקרא: <שם>".
בחירת גופים וסדר עדיפות
הנציג מסמן גוף אחד או יותר. סדר הבחירה קובע badge עדיפות ממוספר (1,2,3…) שקובע גם את סדר תור ה-OTP. ב-sidepanel אפשר גם גרירה לשינוי סדר.
Pre-flight — בדיקת שדות לפני הרצה
ה-sidepanel מריץ preflightMissing() לכל גוף: הכרטיס מציג "✓ מוכן לבדיקה" או "⚠ חסר: <שדות>". לפני הרצה confirm() מפרט מה חסר וממליץ להשלים ב-CRM. מטרה: לא להיתקע באמצע מול לקוח על הקו.
הרצה — פתיחת טאב לכל גוף
חובה לפחות גוף אחד + id_number, אחרת alert. startChecks: מסובב session פרוקסי (IP ישראלי טרי), מאפס תור OTP, פותח טאב לכל גוף בהשהיה מדורגת. הגוף עובר ל-running.
מילוי אוטומטי של הטופס
בכל טאב, agent.js הישן או Engine V4 מזהה מסך אחר מסך וממלא: סכום (תמיד מקסימום), מטרה, שאלות רגולציה, כתובת, פרטי בנק. הפאנל מציג "תצוגה חיה" טקסטואלית (אין screenshot אמיתי לטאב-רקע ב-MV3).
OTP — התערבות הנציג
כשגוף מגיע ל-OTP, נשלח SMS לנייד הלקוח. overlay ממותג מוזרק לטאב ה-CRM (שם הנציג מסתכל, לא בטאב-הרקע). תור טורי מבטיח שרק גוף אחד שולח קוד בכל רגע. הנציג מבקש בטלפון את 6 הספרות ומדביק. הקוד מסונן לספרות, חייב ≥4.
מסך כרטיס אשראי — לעולם לא הבוט
הבוט לעולם לא מקליד מספרי כרטיס. overlay מבקש מהנציג למלא כרטיס+תוקף וללחוץ המשך. המנוע ממתין (עד 180 שנ') שה-URL יעזוב את /card וממשיך אוטומטית.
קליטת תוצאה
detectResult() מסווג אושר/נדחה מטקסט עברי, ומחלץ סכום/ריבית/חודשי מהמסך. reportResult משמיע צליל (אושר 1200Hz / נדחה 400Hz; stuck/manual שקטים בכוונה), דוחף ל-history, ל-webhook ולדשבורד.
סיכום, השוואה והמשך תהליך
טאב התוצאות בונה טבלה חוצת-גופים ומדגיש "🏆 ההצעה הטובה ביותר" (ריבית מאושרת נמוכה ביותר) או "❌ נדחה בכל הגופים". הנציג יכול "העתק סיכום" או "וואטסאפ" (wa.me לנייד הלקוח), ולהזין תוצאה ידנית (agent='ידני'). מכאן ממשיכים למכירה/תשלום מול הלקוח.
"לקוח אמיתי הוא לא QA. תקיעה אצל לקוח = חוויה רעה, גם אם תיקנו רטרואקטיבית." — חן, תובנת היסוד לאסטרטגיית V4
03

גופי המימון — הטבלה המלאה

חמישה גופים, כל אחד עם ארכיטקטורת אתר שונה, מנגנון OTP שונה, וסכום/מטרת הלוואה קבועים. הכותרת של background.js מסכמת: "ירושלים רץ חופשי, כאל מזהה אוטומטית, שאר אחד-אחד."

גוףדומיין / טכנולוגיהסכום מקס'מטרת הלוואהOTPאיך הבדיקה עובדת + מוזרויות
בנק ירושלים 🏛️ bankjerusalem.co.il /credit · Angular 13 + Material · partner=kranot 200,000 כיסוי חובות / סגירת התחייבויות never רץ חופשי, ללא תור 6 צעדים (סכום → מטרה → מצב משפחתי+מגורים → תעסוקה+ותק+הכנסה+התחייבויות בסליידרים → פרטים אישיים → כתובת ואז עצירה בכרטיס). כל 5 הטפסים ב-DOM בו-זמנית → צריך לזהות את הטופס הפעיל. סלקטורים לפי aria-label (IDs דינמיים). מסנן בנר "קדימה, ממשיכים" שחוזר אחורה ל-step 1. rate-limit קשיח: >5 שליחות/שנייה → תקלה 306 → kill-switch _jlmBlocked, צריך incognito חדש. סליידרים מונעים במקלדת (Home/PageUp/Arrow) לפי aria-valuenow. פאנל דיבאג צף.
הפניקס 🔥 myloans.fnx.co.il /xtafnit · Kendo UI (לא HTML5) · SPA בכתובת אחת 150,000 מטרה אחרת always חובה תור כל המסכים מזוהים לפי טקסט ולא URL (SPA כתובת-יחידה). כפתור ראשי bPrimary יציב בכל המסכים. סכום=150k מזין requestLoanAmount ומסנכרן סליידר. 3 שאלות (לא סורבתי / אין נהנה נוסף / לא איש ציבור) דרך role=radio. תעסוקה דרך label[for]. TURBO מבוטל לפניקס — היה מכבה בחירות Kendo. נקודת תקיעה ידועה: מסך ריבית/החזר ("המשך").
ישראכרט 💳 isracard.co.il /loans/bingo → digitalloans · Angular + Shadow-DOM 200,000 מטרה אחרת always חובה תור הכי כבד בדרישות שדות. סליידר Wix (pointer-events על קצה המסלול, RTL). שמות פרטי/משפחה נחתכים ל-10 תווים; מיקוד נכפה ל-7 ספרות (cityZipMap, ברירת מחדל 9101001). כתובת "צוברת זבל >50 תווים" → forceClear. J5="יש כרטיס אשראי" → תמיד לא. CreditReport דורש 'מאשר' מדויק (דוחה 'לא מאשר'). דורש שחרור נעילת launcher (v4launch::/v4errrec::) אחרת נתקע ב-CTA. לחיצה מהירה מדי על "מעניין אותי" → ErrorPage.
כאל 💎 cal-online.co.il /landing/loan2allg · Angular Material · הכי יציב 200,000 הוצאה אחרת sometimes זיהוי אוטומטי ניתוב לפי URL. חובה ללחוץ את הכפתור הכחול "להלוואה מהירה" (לא טופס הליד הוורוד). ה-submit האמיתי הוא "אפשר להמשיך" (type=submit) — /המשך/ לא תופס את "להמשיך" (יש יו"ד!), ו"אישור" הוא כפתור מודאל שגוי. "מעניין אותי" דורש gesture אמיתי (isTrusted) שתוסף לא יכול לזייף → מבקש מהנציג ללחוץ. /card = תמיד ידני. ng-invalid נחשב קוסמטי — כאל מקבל server-side. לקוח כאל קיים = flow נפרד מבודד לפי host.
מקס ⭐ max.co.il · lightweight · block יחיד 200,000 (ריק) always חובה תור הפשוט ביותר: login ת"ז → כניסה → OTP → מספר חשבון → "הלוואה אונליין" → סכום מקס + צ'קבוקסים → אישור תנאים. עובד טוב, אבל חן מציין שמקס שינו אתר פעמיים בשנה וימשיכו.

04

05

כללי העסק — זכאות, ניתוב, פסילות, ספי החלטה

סכום ומטרה — קבועים לחלוטין

סכום ההלוואה הוא תמיד המקסימום לכל גוף (ירושלים/ישראכרט/כאל/מקס 200,000; פניקס 150,000). אם שדה הסכום נמוך יותר — ממלאים מחדש למקס. מטרת ההלוואה קבועה לפי גוף: ירושלים "כיסוי חובות / סגירת התחייבויות"; ישראכרט+פניקס "מטרה אחרת"; כאל "הוצאה אחרת".

תשובות רגולציה — מקודדות קשיח

הלבנת הון / טרור / סורבת בעבר → תמיד "לא" / "לא סורבתי"
איש/אשת ציבור (PEP) → תמיד "לא"
נהנה נוסף → "אין נהנה נוסף"
מקור החזר → "כן, יש לי הכנסה"
אישור מאגר אשראי → תמיד "מאשר" (+צ'קבוקסים)
עיסוק נדל"ן/הימורים/מט"ח → "לא בתחום"
מקור כספים (ישראכרט) → "משכורת"
תעסוקה רק עצמאי מפורש→"עצמאי/ת", אחרת "שכיר/ה" / כאל "במשרה מלאה"
מגדר / תעסוקה אף פעם לא לנחש בטופס מחייב

ב-V4 הדטרמיניסטי: ערך מגדר/תעסוקה לא-מוכר מתמפה ל-'' → _findClickable מחזיר null → needs-ai → עצירה נקייה לנציג. המערכת לעולם לא מנחשת מגדר או סוג תעסוקה בטופס מחייב.

ניתוב מגורים — כלל ה"אצל ההורים" (סיכון ציות!)

כלל אוטומטי בירושלים step 3: אם ב-CRM מגורים="שכירות/משכנתא" אבל monthly_housing_payment (n18) חסר → הבוט מחליף אוטומטית ל-"אצל ההורים" כדי לא להיתקע על סליידר ההחזר. זה לא תמיד נכון ועלול לייצר אישור שלא משקף את מציאות הלקוח — חשיפה משפטית.

פסילות ותוצאות

דחייה היא תוצאה תקינה (done), לא תקיעה. מזוהה במילות-מפתח עבריות שלמות בלבד (למנוע false-positive משיווק חיובי). דוגמאות דחייה: "לא נוכל לאשר", "נדחתה", "אינך זכאי", "הבקשה לא אושרה". דוגמאות אישור: "אושר", "ההלוואה שלך", "אישרנו", "מזל טוב". מקרה מיוחד: פועלים "כבר יש לך חשבון אצלנו" = נדחה (לקוח קיים).

הבעיות הכואבות היום

#1 הכאב המרכזי התהליכים הכפולים

זו הבעיה הכי חמורה. יש ריבוי מימושים חופפים שרצים על אותו לקוח/מסך:

  • כאל = שלושה מימושים חופפים (auto-pilot IIFE legacy + heuristicCal legacy + heuristicCalFast) ועוד מנוע V4. הערה מפורשת: TURBO "היה מתחרה בהם ומכבה בחירות Kendo".
  • ישראכרט — heuristicIsracardKycSteps ו-heuristicIsracardSimpleChoiceStep מכסים את אותם מסכים.
  • OTP בשני נתיבים מקבילים: legacy (requestOTP/otpCompleted/checkOTPTurn) מול v4 (v4OtpAcquire/Release/ShowCrmOtp) — currentOTP משותף, סיכון desync.
  • שני מימושי overlay ל-OTP: crm-otp-overlay.js על טאב ה-CRM מול showOtpOverlay inline על טאב הגוף — עלולים להתפצל. ה-sidepanel אפילו מסתיר את ה-OTP section שלו ("OTP handled only by CRM popup overlay") אך משאיר קוד חצי-מחווט מת.
  • כפל-runMission — auto-run + message יכולים להריץ שני ScreenRunners / שני חלונות OTP. נשמר בכוח ע"י נעילות _missionRunning / v4launch::.
  • איפוס נעילה גלובלי שבור: איפוס {} במקום מחיקת הגוף הספציפי שבר את מוני ה-SMS/reload של גוף מקביל — תוקן ל-delete _of[b].

התוצאה: בעיית 7 ה-SMS — כל התכנון תלוי בהצבת _lastOtpCode רק אחרי לחיצת submit אמיתית, אחרת נשלחים קודים כפולים והתהליך נתקע.

#2 reactive במקום proactive

agent.js ~9,000 שורות עם selectors קשיחים — כל שינוי קטן באתר בנק שובר → תיקון ידני → נבדק חי על לקוח אמיתי. 4 גרסאות גיבוי ב-6 ימים = שינויים יומיים, שום דבר לא יציב. כל הכלים הקיימים (AI chat-to-fix, hot selectors, dashboard) מתקנים אחרי שהלקוח כבר נפגע.

#3 תקלה 306 בבנק ירושלים

rate-limit קשיח: >5 שליחות/שנייה → חסימה "תקלה 306 / הקלדות שגויות" → kill-switch, צריך incognito טרי. בנוסף: כל 5 הטפסים ב-DOM בו-זמנית, ובנר "קדימה, ממשיכים" מתחזה לכפתור המשך ומנווט אחורה ל-step 1. גם: מילוי שדה-אחד-לאיטרציה נכפה כי מילוי-הכל-מיידי מזוהה כבוט → 306.

#4 סליידרים ששקטים חוזרים לברירת מחדל

הכי קריטי מבחינת נכונות: ב-step 4 של ירושלים 3 סליידרים מזוהים לפי aria-valuemax ומתבלבלים, וסליידרים מתאפסים לברירת מחדל אחרי שהוגדרו — הבוט ממשיך עם ערכים שגויים ועלול לאשר הלוואה על נתונים לא נכונים. ב-V4: Angular עלול לשים max='0' (מחרוזת truthy) — נבדק מספרית; setSliderMax חייב להגיע ל-aria-valuemax אחרת needs-ai.

#5 שברירויות נוספות
  • ישראכרט SPA "רועד" — צריך 1-2 reloads, נוחת ב-errorpage תכופות (תקרת retry הועלתה ל-6). שדה ת"ז בלוגין לפעמים ב-iframe לפעמים בדף ראשי → #tz-input לא אמין.
  • פרוקסי sticky-IP נופל ב-idle: בזמן שהנציג מקליד OTP אין תעבורה → ה-IP מתחלף → המסך הבא נוחת על IP אחר → חסימה. ממותן רק ע"י keep-alive 35 שנ'.
  • MV3 SW נרדם אחרי ~30 שנ' → הבוט קופא על sendMessage. עוקפים עם WebSocket + timeout 2.5 שנ'.
  • קליטת תוצאה חסרה — הבוט מסיים אך לא שולח session.end עם amount/rate/period; הנציג קורא ידנית. ה-endpoint קיים, agent.js פשוט לא שולח.
  • ng-invalid מתעלמים ממנו ("קוסמטי, כאל מקבל server-side") — עלול לשלוח נתונים שגויים.
  • כתובת ישראכרט צוברת זבל >50 תווים — עוקף עם forceClear, לא תוקן.
  • datacenter VPN חסום ב-ASN ע"י הבנקים; IP משותף נחסם אחרי כמה בדיקות → צריך residential IL עם סבב לכל בדיקה.
#6 פערי ייצור ומשפט
  • אין כתיבה חזרה ל-CRM — תוצאות הולכות רק ל-webhook/history; סטטוס ה-CRM לא מתעדכן.
  • שרת v3 = Phase 0: אין DB, אין auth (localhost), אירועים בזיכרון + events.jsonl.
  • ANTHROPIC_API_KEY חסר בשרת → AI chat-to-fix ("ה-killer feature") לא פעיל.
  • Terms of Service ומדיניות פרטיות לא קיימים — חובה לפני ייצור, בבדיקת עו"ד.

08

המלצות — מה לבנות ב-Bingo CRM

המטרה: לשקף את התפעול נכון ולפתור את הכאב. סדר בנייה נעול, מהשבור ביותר ליציב: 1) בנק ירושלים · 2) פניקס · 3) מקס · 4) ישראכרט · 5) כאל. כאל נבחר כ-pilot ל-V4 כי הוא הכי יציב — להוכיח שהמנוע לא שובר את מה שכבר עובד.

A מנוע יחיד — לחסל את התהליכים הכפולים

להעביר כל גוף ל-ScreenRunner דטרמיניסטי יחיד (server-brain) ולמחוק את שלושת מימושי כאל / כפל ישראכרט / שני נתיבי OTP / שני overlay-ים. עיקרון V4: "מפסיקים לקודד איך (selectors), מקודדים רק מה (כוונה)". גוף = קובץ ~40 שורות declarative intent-flow. mutex OTP אחד ויחיד. overlay OTP אחד ויחיד (על טאב ה-CRM).

B Selectors חמים בשרת + ריפוי-עצמי 3 שכבות

כל selector = עד 5 אסטרטגיות מסודרות (CSS / XPath / :has-text()). Resolver: שכבה 1 cache (~99%, חינם, מיידי) → שכבה 2 Claude קורא DOM snapshot כשה-cache נשבר (נשמר כ-cache חדש) → שכבה 3 נציג מצביע ב-side-panel. תיקון = עריכת JSON בדשבורד, מתפשט תוך 60 שנ' דרך /api/config. מפתח selector: body.step.field (למשל jerusalem.step3.continue).

C Pre-flight אמיתי — לעצור להיות reactive

לפני שהלקוח על הקו: הבוט פותח את אתר הבנק בטאב רקע, מנווט עד רגע לפני login, ה-AI מוודא שה-DOM נראה כצפוי. ירוק ("מוכן") → הפאנל מתקדם ל-OTP. אדום → ה-AI מציע תיקון selector, חן מאשר, ורק אז מתחילים עם הלקוח. "לקוח אמיתי הוא לא QA."

D מוניטור סינתטי לילי + Regression בלי לקוחות

קרון ב-~02:00 מריץ בדיקה מלאה לכל גוף עם "לקוחות" פנימיים (חן + עובדים מסכימים), OTP למספר פנימי. כשל → מסמן גוף 🔴 לפני יום העבודה. בנוסף: כל ריצה אמיתית נשמרת לספריית recordings; לפני כל שינוי מריצים את המנוע החדש (StaticDriver) על מאות snapshots — 100% pass = בטוח ל-deploy. DOM-diff >15% = אזהרה מוקדמת.

E Canary + Circuit Breaker + Audit

לעולם לא לשחרר selector לא-בדוק לכולם בבת אחת: Canary — נציג 1, אם 3 בדיקות עוברות → 5, אם 10 עוברות → כולם; כל כשל = rollback אוטומטי. Circuit breaker: כשל >30% בשעה האחרונה → עצירת הגוף + התראה. כל שינוי נשמר עם מי/מתי/למה (audit), הפיך ב-click אחד. selector מסומן valid רק אחרי 3 נציגים שונים שהריצו בהצלחה.

F צעד אישור מגורים/הכנסה (ציות)

לפתור את חשיפת ה"אצל ההורים": צעד אישור לפני ההרצה שנותן לנציג לאשר/לתקן מגורים + הכנסה + ילדים + גיל + תעסוקה — כדי לא לתת ללקוח אישור לא-מדויק. בנוסף: כתיבה חזרה ל-CRM של סטטוס התוצאה (amount/rate/period/monthly) — הפער הכי בולט היום.

G קליטת תוצאה מובנית + הקשחת ייצור

לחבר את session.end עם result JSON (ה-endpoint כבר קיים). להשלים Phase 5: DB אמיתי + auth + HTTPS + JWT (30 יום, disable מבטל מיידית), התראות Resend/Telegram (server-down + Sentry חדש מעירים בלילה; שאר עד 07:00), redaction PII בלוגים/snapshots, ולבסוף Terms + Privacy בבדיקת עו"ד ו-ANTHROPIC_API_KEY על השרת כדי להפעיל את ה-chat-to-fix.

סיכום מנהלים — מה מייצג הצלחה

נציג בוחר גוף+לקוח → pre-flight ירוק לפני OTP → הלקוח מקבל SMS פעם אחת בלבד → הבדיקה רצה על מנוע דטרמיניסטי יחיד → תוצאה מובנית נכתבת חזרה ל-CRM. כשבנק משנה אתר: המוניטור הלילי תופס, חן מתקן selector בדשבורד, Canary מוודא, וכל 17 הנציגים מקבלים תוך 60 שנ'. 0 ZIPים. 0 לקוחות כ-QA.
